= Module 6: Enable self-service with templates
:source-highlighter: rouge
:toc: macro
:toclevels: 1

Parasol's developers can now discover existing services in the catalog and query it with AI. But what about creating new ones? Today, spinning up a new application means copying an old project, manually configuring CI/CD, writing deployment YAML, and hoping you remembered all the security requirements.

Software templates are the golden paths of platform engineering. They encode your organisation's best practices into a self-service workflow. When a developer uses a template, they get a production-ready application without writing a single line of infrastructure code.

**What the template delivers:**

* **Zero YAML required** -- developers write Java, Node.js, or Python; the platform team's Helm charts handle all infrastructure configuration
* **Security by default** -- automated SonarQube code analysis, Advanced Cluster Security image scanning, and SBOM generation with Trusted Profile Analyzer monitoring
* **GitOps-driven deployment** -- changes flow through build → dev → prod namespaces via Argo CD, following the platform team's promotion workflow
* **Full observability** -- ServiceMonitors, network policies, and resource limits configured automatically

The golden-path template was already imported in Module 5 alongside the catalog entities. In this module, you'll experience the developer's self-service workflow by running the template and inspecting the platform infrastructure it creates.

== Exercise 1: Explore the template

. Open the **Developer Hub** tab and navigate to the **Create** page (or click the **Self-service** button in the global header)

. You should see the imported software template. Click on it to review:
+
* **Template name and description** -- What the template creates
* **Input parameters** -- What the developer needs to provide (application name, Git organisation, etc.)
* **Steps** -- What the template does behind the scenes (scaffolding code, creating a repository, configuring pipelines, registering the catalog entity)

. Review the template's steps to understand the golden path it implements:
+
.. **Scaffolds application code** -- generates a Quarkus application with LLM client dependencies and External Secrets integration for API keys
.. **Creates GitLab repository** -- sets up version control with webhook triggers for CI/CD
.. **Deploys build infrastructure** -- uses the platform's `build-deployer` Helm chart to create:
   * Tekton pipeline with SonarQube scanning, ACS image scanning, and SBOM generation
   * External Secrets for credentials (GitLab, Quay, SonarQube, ACS, TPA)
   * Webhook-triggered builds on every commit
.. **Provisions multi-environment deployment** -- uses the platform's `app-deployer` Helm chart to create namespaces for dev and prod with:
   * Kubernetes Deployments, Services, and Routes
   * Network policies and ServiceMonitors for observability
   * Horizontal Pod Autoscaling and resource limits
.. **Enables GitOps promotion** -- configures Argo CD Applications for automated sync from GitLab manifests
.. **Registers in catalog** -- adds the component to Developer Hub with ownership, dependencies, and CI/CD integration

== Exercise 2: Run the template

Now experience the golden path as a developer would.

. Click **Choose** on the template to start the wizard

. Fill in the parameters:
+
* **Application name**: Choose a name (e.g., `parasol-claims`)
* **Description**: A short description
* Accept the defaults for other fields

. Click through the wizard steps, reviewing what will be created

. Click **Create** to execute the template

. Watch the progress as the template:
+
* Scaffolds the application code
* Creates the GitLab repository
* Configures the CI/CD pipeline
* Registers the new component in the catalog

. Once complete, click the links to explore:
+
* The new **GitLab repository** with scaffolded code -- notice there's **no Kubernetes YAML**, just application code
* The new **Catalog entity** in Developer Hub
* The **Tekton pipeline** that was triggered automatically -- watch it run SonarQube analysis, build the image, scan it with ACS, generate an SBOM, and upload to TPA

=== Verify

* The template wizard completed successfully
* A new GitLab repository was created with application code (no infrastructure YAML)
* Three namespaces exist: `<app-name>-build`, `<app-name>-dev`, `<app-name>-prod`
* A new component appears in the Developer Hub catalog
* A Tekton pipeline run was triggered with multiple security and quality gates

== Exercise 3: Inspect what the platform built

The template created infrastructure that would take hours to configure manually.

. In the **OpenShift Console** tab, switch to the **Developer** perspective

. Navigate to **Project** dropdown and find the three namespaces created for your application:
+
* `<app-name>-build` -- CI/CD infrastructure (Tekton pipelines, External Secrets, build cache)
* `<app-name>-dev` -- development deployment managed by Argo CD
* `<app-name>-prod` -- production deployment (promoted via GitOps)

. Select the `-build` namespace and explore **Pipelines**:
+
* Click on the running PipelineRun to watch the execution
* Expand the pipeline tasks to see:
  ** `maven-build` -- compiles the application
  ** `sonar-scan` -- static code analysis for vulnerabilities
  ** `generate-sbom` -- creates a Software Bill of Materials
  ** `acs-image-scan` -- scans the container image for CVEs
  ** `acs-image-check` -- enforces security policy gates
  ** `upload-sbom-to-tpa` -- registers the SBOM with Trusted Profile Analyzer for continuous monitoring

. Switch to the `-dev` namespace and explore the **Topology** view:
+
* Notice the Deployment, Service, and Route were created from the `app-deployer` Helm chart
* Click on the Deployment to see resource limits, health checks, and environment variables injected via External Secrets

. In the **Developer Hub** tab, navigate to your new component and click the **CI/CD** tab:
+
* See the pipeline execution integrated directly into the catalog view
* Developers get visibility into build status without leaving Developer Hub

=== Verify

* Three namespaces exist with the expected resources
* The Tekton pipeline shows multiple security gates (SonarQube, ACS, SBOM)
* The dev namespace has a running Deployment created from the platform Helm chart
* CI/CD status is visible in the Developer Hub catalog

== The platform engineering value proposition

This is where platform engineering delivers transformational impact.

**What the developer experienced:**

* Filled in a simple form (application name, description)
* Clicked "Create"
* Got a production-ready application in minutes

**What the platform team delivered invisibly:**

* **Zero infrastructure code for developers** -- no Dockerfiles, no Kubernetes YAML, no pipeline definitions. The `build-deployer` and `app-deployer` Helm charts encode the platform team's standards.
* **Security by default, not by request** -- every application gets SonarQube analysis, ACS vulnerability scanning, SBOM generation, and continuous monitoring via TPA. Developers can't skip the security gates.
* **Standardized deployment patterns** -- network policies, resource limits, health checks, observability (ServiceMonitors), and autoscaling configured consistently across all applications.
* **GitOps-driven promotion** -- changes flow through build → dev → prod namespaces following the platform team's workflow. Developers push code; Argo CD handles deployment.
* **Integrated toolchain** -- External Secrets Operator injects credentials from Vault, Tekton triggers builds from GitLab webhooks, Argo CD syncs from GitOps repos, and Developer Hub provides unified visibility.

**What this means for Parasol:**

* **Faster time to market** -- new applications in minutes instead of weeks spent writing YAML and configuring pipelines
* **Consistent compliance** -- security and quality gates applied uniformly; no "forgot to add the SBOM step" incidents
* **Reduced cognitive load** -- developers focus on business logic in their language of choice; infrastructure is handled
* **Easier maintenance** -- platform team updates the Helm charts once; all applications benefit from improvements

This is the multiplier effect of platform engineering: build the golden path once, enable hundreds of teams to run it reliably.
