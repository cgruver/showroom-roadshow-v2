== The Backstage entity model

Before registering entities, it's worth understanding how the catalog organises information:

* **Component** -- A software unit (service, library, website) owned by a team
* **API** -- An interface exposed by a component (REST, gRPC, event)
* **System** -- A group of related components that form a product or capability
* **Resource** -- Infrastructure dependencies (databases, queues, clusters)
* **Domain** -- A business area that owns systems

Each entity is defined in a `catalog-info.yaml` file that typically lives alongside the source code. The team that owns a component is responsible for maintaining its `catalog-info.yaml` -- just like they maintain the code itself. Developer Hub reads these files and builds the catalog graph.

Not every entity needs a hand-crafted YAML file, though. Integrations like the GitLab discovery provider (which you enabled in the previous module) can scan repositories and auto-register any `catalog-info.yaml` files they find. Other providers go further -- the Keycloak provider you configured automatically imports users and groups from your identity provider, and CI/CD integrations can surface pipeline and deployment data without any catalog changes at all.

== What changed?

The only difference between this overlay and the previous one is a new `catalog.locations` entry in the app-config pointing at a single catalog index:

[source,yaml]
----
catalog:
  locations:
    - type: url
      target: https://gitlab-gitlab.{openshift_cluster_ingress_domain}/parasol/parasol-entities/blob/main/catalog-index.yaml
      rules:
        - allow: [Component, System, API, Resource, Location, Domain, Group]
----

This single location points to a `catalog-index.yaml` that references all of Parasol's entity definitions -- Groups, Domains, Systems, Components, and APIs. Developer Hub reads the index, follows its targets, and builds the full catalog graph. Using an index file like this is a common pattern for managing large catalogs without listing every entity file individually.

**Key takeaway:**

The software catalog is more than a service registry -- it's a **knowledge graph** that models your entire software landscape. Systems, components, APIs, resources, teams, and documentation are all connected in a queryable structure.

For humans, this means:

* **Instant discovery** -- find services, APIs, and docs without filing tickets
* **Visual architecture** -- understand system dependencies through diagrams
* **Integrated information** -- CI/CD status, topology, and documentation in one place

For AI agents (coming in Module 7), this means:

* **Programmatic access** via MCP to query catalog entities
* **Contextual answers** grounded in authoritative, up-to-date documentation
* **Relationship traversal** to answer questions like "what depends on this API?" or "which team owns the Billing service?"

The catalog isn't just documentation -- it's **operational intelligence** accessible to both humans and machines.
