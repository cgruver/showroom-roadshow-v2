== The Backstage entity model

Before registering entities (like the Parasol Insurance component in the prior module), it's worth understanding how the catalog organises information:

* **Component** -- A software unit (service, library, website) owned by a team
* **API** -- An interface exposed by a component (REST, gRPC, event)
* **System** -- A group of related components that form a product or capability
* **Resource** -- Infrastructure dependencies (databases, queues, clusters)
* **Domain** -- A business area that owns systems

Each entity is defined in a YAML file (commonly named `catalog-info.yaml`) file that typically lives alongside the source code. The team that owns a component is responsible for maintaining its `catalog-info.yaml` -- just like they maintain the code itself. Developer Hub reads these files and builds the catalog graph.

Not every entity needs a hand-crafted YAML file, though. Integrations like the GitLab discovery provider (which you enabled in the previous module) can scan repositories and auto-register any `catalog-info.yaml` files they find. Other providers go further -- the Keycloak provider you configured automatically imports users and groups from your identity provider, and CI/CD integrations can surface pipeline and deployment data without any catalog changes at all.

. Open https://gitlab-gitlab.{openshift_cluster_ingress_domain}/parasol/parasol-entities/-/blob/main/parasol-foundations.yaml[`parasol-foundations.yaml`,window=_blank] to see how Domains and Systems are defined

+

+
Notice how the diagram shows:
+
* **Components** grouped into their parent System

+
This opens the full relationship graph with additional depth. You can:
+
* **Zoom and pan** to explore the full topology
* **Click nodes** to see entity details
* **Trace dependencies** across multiple levels (e.g., which APIs a component uses, which resources those APIs depend on)
+
This is the catalog's power: it doesn't just list services, it models the relationships between them. When a developer asks "what does the Billing service depend on?", the graph shows the answer immediately.

* **Architecture decision records (ADRs)** explaining why the Billing system is structured this way
* **PCI-DSS compliance information** documenting how payment data is handled securely
* **Onboarding guides** for developers joining the Billing team
+
Notice that this documentation is discoverable through the same interface developers use to find services and APIs. It's not buried in Confluence or a wiki -- it's registered in the catalog alongside the code.

== Exercise 4: Query the catalog with Lightspeed

You've just explored the catalog visually as a human. Now see how AI agents can query the same catalog programmatically via the Model Context Protocol (MCP).

[NOTE]
====
The overlay you just deployed includes **Lightspeed** -- an AI assistant integrated into Developer Hub. Lightspeed runs as sidecar containers (llama-stack for LLM inference, lightspeed-core for the service layer) with MCP access to the catalog API.

This means Lightspeed can query real catalog data in real-time -- not generic documentation, but your actual Systems, Components, APIs, and TechDocs.
====

. Open the **Developer Hub** tab and look for the **Lightspeed** icon in the top-right corner (chat bubble icon) or in the left sidebar

. Click the Lightspeed icon to open the chat interface

. Try asking Lightspeed about the catalog you just explored:
+
* _"How does Parasol handle PCI compliance?"_
  ** Lightspeed uses MCP to query the catalog's TechDocs API
  ** Retrieves the Billing & Payments documentation you saw in Exercise 2
  ** Returns an answer grounded in the actual compliance documentation
+
* _"What components are in the API Gateway System?"_
  ** Lightspeed queries the catalog API for the API Gateway System entity
  ** Lists the actual Components you saw in the System Diagram
+
* _"What does the Claims service depend on?"_
  ** Lightspeed traverses the catalog's relationship graph
  ** Returns the API and Resource dependencies

. Notice how Lightspeed's answers reference **real entities** from your catalog, not generic responses

. Try one of the pre-configured suggested prompts if available in the chat interface

=== Verify

== What changed?

This overlay added significant functionality to Developer Hub:

1. **Catalog locations** -- Four catalog.locations entries:
   - `parasol-entities/catalog-index.yaml` (Parasol's architecture: Systems, Domains, Components, APIs)
   - `parasol-store/catalog-info.yaml` (example Component)
   - `parasol-store-api/catalog-info.yaml` (example API)
   - `rhdh-template-developer-self-service/location.yaml` (golden-path templates)

2. **RBAC policies** -- Role-based access control:
   - Platform engineers: full catalog management, template execution
   - Developers: read catalog, execute templates, manage their own entities

3. **Lightspeed AI assistant** -- Three sidecar containers added to the Backstage pod:
   - `llama-stack` -- LLM inference with qwen3-14b model
   - `lightspeed-core` -- Service layer coordinating chat UI, LLM, and MCP
   - `init-rag-data` -- Init container that loads RHDH product documentation embeddings

4. **MCP integration** -- Model Context Protocol configuration:
   - `mcp::backstage` server registered in Lightspeed config
   - Points to `http://backstage-developer-hub.rhdh.svc.cluster.local/api/mcp-actions/v1`
   - Gives Lightspeed structured access to catalog API and TechDocs API
   - 15+ dynamic plugins including MCP tools, GitLab, ArgoCD, Kubernetes, Tekton

The catalog index pattern (one Location pointing to a file with many targets) is a common approach for managing large catalogs without listing every entity individually.
